# 双端语言功能设计说明

> 面向网站端与 Android App 端的语言（语音）功能呈现与交互设计
> 版本：v1.0 · 2026-10-09

---

## 一、设计前提：为什么必须重建发音体系

在动手设计界面之前，先记录三个已经通过实测确认的硬约束。这三条决定了整个设计的形态，跳过任何一条都会做出「看起来对、实际不工作」的方案。

### 1. 设备不一定有英语语音

`window.speechSynthesis` 对象几乎在任何浏览器里都存在，但 `getVoices()` 返回的列表可能一条英语都没有——本机实测为 3 个语音、0 个英语语音。此时调用 `speak()` 既不触发 `onstart` 也不触发 `onerror`，**完全静默**。

> 结论：不能用「`speechSynthesis` 是否存在」判断可用性。必须实测语音列表。

### 2. 现成的云端发音接口只支持单词

以有道词典接口为例：

| 文本 | 返回 |
|---|---|
| `hello` | 200 |
| `thank you` | 200 |
| `Nice to meet you` | 200 |
| `I am writing to confirm` | **500** |
| `I don't expect to have this ready by Friday` | **500** |

而本项目口语、日常交流、对话示例三个模块的核心内容**恰恰全是整句**。这条接口无法支撑核心场景。

### 3. Android WebView 不实现 Web Speech API

App 内嵌 WebView 中，网页看到的语音总数恒为 0，但 App 实际走的是原生引擎。**直接展示「0 个语音」会让用户以为坏了**，文案必须说清这是两条不同的链路。

## 二、发音能力分层

不发音和发音不准一样糟糕，一句错读比一句不读更误导人。因此不设「开/关」二元状态，而是四层递进，每层都能独立工作：

| 层 | 能力 | 覆盖范围 | 依赖 | 延迟 |
|---|---|---|---|---|
| **0 · 在线发音** | 13 种英/美/澳 Natural 音色 | 单词 / 短语 / **整句** | 服务运行中 | 首次 1-4s，之后 5ms |
| **1 · 本机语音** | 系统自带音色 | 单词 / 短语 | 已装英语语音包 | 即时 |
| **2 · 云端发音** | 有道词典 | **仅单词 / 短语** | 联网 | 300ms |
| **3 · 引导提示** | 无声，但给出解法 | — | — | — |

### 决策规则

```
0 层可用？ ──是──→ 用 0 层
   │否
   ▼
本机有英语语音？ ──是──→ 用 1 层
   │否
   ▼
已授权云端？ ──是──→ 用 2 层
   │否
   ▼
弹引导（不静默）
```

**0 层优先级高于 1 层**，即使本机装了语音包也优先用在线发音。理由：代理的音色与可用性由服务端保证，不会因为换了台电脑、少装个语音包就突然失声；同时它能读整句，而本机语音在部分 Android 设备上对长句的发音明显不稳。

**唯一例外**：用户在设置里显式选「只用本机」或「只用云端」时，严格尊重该选择，不自动切回 0 层。

### 三条工程约束（易踩坑，已在代码中处理）

1. **`resolveMode()` 必须把代理判定放在最前面。** 早期版本只检查「设备有没有英语语音」，在没有语音包的机器上直接返回 `none`，代理代码全部就位却一条都走不通——这是本项目最隐蔽的一个 bug。
2. **`supported()` / `speakSequence()` 的早退也要放行代理。** 代理走 `<audio>` 播放，不依赖 `speechSynthesis`，被这些早退拦住会同样失效。
3. **`isSpeaking()` 必须纳入代理音频状态。** 否则连续朗读队列会在每一句上误判为「已结束」而中断。

## 三、各模块的语言功能设计

### 总览页

| 项 | 设计 |
|---|---|
| 入口 | 顶部导航第 1 项 |
| 呈现 | 本周高频词与在读材料，各带一枚可点发音的小喇叭 |
| 交互 | 单击朗读当前词；连读按钮按当天清单依次播报 |
| 移动端 | 卡片单列，发音按钮置于卡片右下角（拇指可达区） |

**设计取舍**：总览页不做大块音频控件。这个页面的任务是让用户 3 秒内知道「今天该干什么」，音频在这里只承担确认作用，不承担学习作用。

### 词汇

| 项 | 设计 |
|---|---|
| 入口 | I · 认知输入 |
| 呈现 | 单词卡正面单词 + 🔊，音标行下方 |
| 交互 | 点 🔊 读单词；**慢速**按钮读两遍（常速 + 0.65×） |
| 反馈 | 已朗读的词在列表里留一个极浅的暖色底，一眼能看出哪些读过 |
| 移动端 | 单词卡顶部贴边，🔊 放在右上（不与手指滚动区冲突） |

**深度讲解联动**：进入单词深层讲解后，其中出现的**例句、搭配、辨析句**各自独立可点读。这一点很重要——学习者卡住往往不是单词不认识，而是不知道它在句子里怎么用，只读单词音标解决不了。

### 口语

| 项 | 设计 |
|---|---|
| 入口 | III · 场景运用 |
| 呈现 | 场景卡片（10 类 / 82 句），每句独立一行 |
| 交互 | 整句朗读；**逐句跟读评测**（需设备支持语音识别）；本段均分统计 |
| 反馈 | 每句给词准确率 / 语速 / 置信度；未识别词与多识别词分别标色 |
| 移动端 | 跟读按钮行贴卡片底部展开，避免横向拥挤 |

整句朗读是本模块的**第一优先需求**——这也是旧云端接口返回 500 的那类文本。

### 日常交流

| 项 | 设计 |
|---|---|
| 入口 | III · 场景运用 |
| 呈现 | 4 个 tab：分类浏览 / **对话示例** / 场景演练 / 随机抽句 |
| 对话示例 | 17 段对话 / 97 句 / 44 个重点表达，教材式排印（非聊天气泡） |
| 交互 | 整段连续朗读、单句朗读、逐句跟读评测 |
| 联动 | 任一表达可反查到「它在对话中怎么被用的」，跳转到对应段落并高亮 |
| 移动端 | 对话左右列改单列（A 在上、B 在下），保留说话人标签与颜色区分 |

**为什么用教材式排印而不是聊天气泡**：气泡隐含「即时对话」的语境，而学习场景需要的是「可反复研读的书面材料」。排印式布局支持逐行扫描与对照，恰好匹配使用意图。

### 阅读

| 项 | 设计 |
|---|---|
| 入口 | III · 场景运用 |
| 呈现 | 分级短文，行内可长按取词 |
| 交互 | 段落朗读；点任意单词单独读；划词取词后发音卡可试听 |
| 排版约束 | 朗读时当前句高亮，便于跟读定位 |

### 词根词缀 / 音标口型

| 项 | 设计 |
|---|---|
| 入口 | II · 理解解析 |
| 呈现 | 词根卡片 + 音标 + 口型动画说明 |
| 交互 | 词根读音可点（多数词根无标准音，需明确标注「参考读法」）；例词逐个可读 |
| 反馈 | 音标模块的口型图与实际发音需一致，否则会教错——口型图是静态的，发音用真实音频兜底 |

### 诗歌名句

| 项 | 设计 |
|---|---|
| 入口 | IV · 审美拓展 |
| 呈现 | 诗句 + 译文 + 出处 |
| 交互 | 整句朗读；**诗行节奏连读**（按行切分，行间短停顿） |
| 设计说明 | 诗歌的节奏本身就是教学内容。整段 TTS 会把韵律压平，所以按行切分并保留可调停顿 |

### 发音设置

| 项 | 设计 |
|---|---|
| 入口 | 工具分组（不参与四阶段学习链） |
| 网页/设备状态卡 | 运行环境、在线服务连接状态、系统语音总数、其中英语语音数、当前实际使用哪一层 |
| 在线发音卡 | 连接检测（带「重新检测」）→ 音色按用途分组 → 整句试听 / 慢速跟读 |
| 发音方式 | 自动 / 只用本机 / 只用云端 |
| 语速 | 0.5×–1.5×，实时文字描述（"0.65× · 偏慢，适合跟读"） |
| 语音包指引 | 仅在确实缺英语语音时出现，按 Windows / Android / iOS 分平台列步骤 |

**信息层级**：状态标签的判定顺序是「在线可用 → App 原生可用 → 本机可用 → 云端 → 缺语音包 → 不支持」。代理可用时必须排第一，否则会误导用户去装根本不需要的语音包。

**故障文案必须区分两种失败**：服务没启动（给启动命令）与设备有问题（给安装步骤）。把这两者混为一谈会让用户反复试错。

## 四、音质设计

「音质差」是个笼统的抱怨，实测拆开后发现有三个独立的成因，分别用不同手段解决。

### 成因一：音频码率不足（直接原因）

原实现用 `audio-24khz-48kbitrate-mono-mp3`，实测**真实码率仅 80kbps**。这个档位会砍掉高频泛音，齿音（s、sh、f）和摩擦音（th、v）发糊，元音听起来闷。

服务端实测结论：

| 格式 | 真实码率 | 可用 |
|---|---|---|
| `audio-24khz-48kbitrate-mono-mp3` | 80kbps | 可用（音质差） |
| **`audio-24khz-96kbitrate-mono-mp3`** | **160kbps** | **可用（当前采用）** |
| `audio-48khz-*` 全系列 | — | **服务端直接关闭连接** |

采样率被服务端锁在 24kHz，无法提升；唯一可用的杠杆就是码率翻倍。**96kbps 是上限，再往上调只有 48kHz，而那个服务端不接受。**

### 成因二：文本没被正确朗读（更隐蔽）

学习内容里有大量缩写和符号。原样送进 TTS，`Mr.` 会被念成字母「M-R」，`&` 会被跳过或念成「and」——用户听到的是错的读音，主观感受就是「音质差」，但问题根本不在音频上。

`prepText()` 只改「怎么读」不改「读什么」：展开缩写（`Mr.`→`Mister`、`e.g.`→`for example`）、符号口语化（`%`→`percent`、`&`→`and`）、归一化空白（多个空格会让某些引擎插入多余短停顿）。

### 成因三：13 个音色平铺，用户无从选择

音色名 Aria / Jenny / Sonia 对学习者零信息量。把它们排成同样式的网格，用户只能靠猜，于是随手选一个不适合的，然后归因于「音质差」。

现按用途分组：

| 分组 | 音色 | 说明 |
|---|---|---|
| **跟读首选** | Aria、Sonia、Jenny、Guy | 咬字清晰、语速适中，最适合逐句对照 |
| **其他音色** | Ryan、Christopher、Libby、Natasha、Michelle、Eric | 各口音备选 |
| **自然童声** | Ava、Emma、Andrew | 最接近真人，但连读多，初学阶段反而不易听清 |

点击任一音色立即用该音色朗读一句，用户直接听出差别而不必盲选。

### 两个必须记住的服务端限制

1. **SSML 只能极简**。`<break>`、`<mstts:express-as>`、`<prosody>` 放在 `<voice>` 外层——**任何一种都会让服务端直接关闭连接，且不报错**。所以停顿只能靠「切分多句、分段合成、客户端拼接」，不能靠标签。
2. **失效音色要主动剔除**。`en-US-JaneNeural`、`en-US-EvanNeural` 实测会静默失败（连接被关闭），必须从可选列表中删掉，否则用户选中后只会觉得「坏了」。

### 缓存必须带格式版本

缓存键里包含 `AUDIO_FORMAT`。换音质后如果不改键，磁盘里旧格式音频会继续被命中返回，用户会以为改动没生效——而实际是缓存没失效。用格式本身当版本，改格式即自动换缓存，无需手工清目录。

## 五、网站端 vs App 端的呈现差异

| 维度 | 网站端 | Android App |
|---|---|---|
| 首选发音路径 | 在线发音（0 层） | **原生 TTS 引擎** |
| 本机英语语音 | 通常有 | **恒为 0，需专门解释** |
| 状态卡文案 | 「在线发音可用」 | 「App 原生发音可用」 |
| 0 个语音的说明 | 无需出现 | **必须出现**，说明这是 WebView 限制而非故障 |
| 代理地址 | 同源 `/tts` 或 `127.0.0.1:8788` | `127.0.0.1:8788`（需放行明文） |
| 安装入口 | PWA 安装按钮 | 已是应用本体，无入口 |
| 离线发音 | 依赖代理服务 | 依赖系统语音包，最可靠 |

### App 端两处必须改的配置

1. **网络明文**：`usesCleartextTraffic="false"` 会直接掐断 WebView 访问 `http://127.0.0.1:8788` 的音频请求。已新增 `network_security_config.xml`，**只对 `127.0.0.1` / `localhost` / `10.0.2.2` 放开明文**，其余域名仍禁止——登录与进度同步的加密要求不受影响。
2. **混合内容**：`MIXED_CONTENT_NEVER_ALLOW` 会阻断 https 页面加载 http 代理音频，表现为「点发音完全没反应且不报错」。已改为 `MIXED_CONTENT_COMPATIBILITY_MODE`。

这两处的共同特征是：**失败时没有任何报错**。这类问题只能靠提前放宽配置来避免，不能等排查。

## 六、移动端适配原则

| 原则 | 具体做法 |
|---|---|
| 触摸目标 | 发音按钮与导航项最小 40px |
| 防聚焦缩放 | 输入框 `font-size: 16px`（iOS 聚焦小于此值会强制放大页面） |

| 长文本 | 说明文字用 `-webkit-line-clamp` 截断，不撑高卡片 |
| 音频解锁 | 首次播放必须在用户手势内触发（`play()` 被拦截后不再自动重试，引导用户再点一次） |

## 七、内容一致性约定

| 规则 | 说明 |
|---|---|
| 语言标注 | 美音、英音、澳音在音色名上明示，不让学习者猜 |
| 缺失音标 | 不留空、不用「暂无」，补齐或标注来源 |
| 整句优先 | 口语/对话/阅读一律提供整句朗读，不只给单词 |
| 变速一致 | 全站语速倍率为同一个语义（0.5 慢 / 1.0 常速 / 1.5 快），不同模块不做反向映射 |
| 发音失败可见 | 任何一条路径失败都必须有反馈，不允许静默 |

## 八、启动方式

```bash
# 在线发音服务（项目根目录）
node tools/tts-server.js

# Windows 可直接双击
tools/启动发音服务.bat
```

网站启动后自动探测 `127.0.0.1:8788`；部署到服务器时把服务挂在域名下的 `/tts` 即可，无需改代码。

### 手机连不上时的排查顺序

服务启动时会在控制台打印两行地址：

```
本机访问：http://127.0.0.1:8788
手机访问（需与电脑同一 WiFi）：
  http://192.168.x.x:8788   (WLAN)
```

**手机端必须填「手机访问」那一行，不能填 `127.0.0.1`** —— 手机上的 `127.0.0.1` 指向手机自己，不是那台跑着服务的电脑。
| 序号 | 检查项 | 说明 |
| --- | --- | --- |
| 1 | 服务是否已启动 | 控制台需打印出「手机访问」地址；若只有 `127.0.0.1` 一行，说明未检测到局域网地址，检查电脑是否连了 WiFi |
| 2 | 监听地址 | 服务以 `server.listen(PORT, '0.0.0.0')` 启动。Node 默认只绑回环，手机即使同一 WiFi 也连不上——这是最容易漏掉的一条 |
| 3 | 是否同一 WiFi | 手机与电脑须连同一路由器；流量走蜂窝网时不可达 |
| 4 | 防火墙 | Windows 首次运行 Node 会弹窗，必须勾选「专用网络」允许。错过则进「Windows 防火墙 → 允许应用通过防火墙」勾上 Node.js |
| 5 | VPN / 代理软件 | 会接管全部流量，导致本地地址打不开，需临时关闭 |

前端侧对应两条设计：

* **地址可编辑**：设置页的「服务地址」是 `<input type="url">` 而非只读文本，手机上才能改成局域网地址；字号固定 `16px`，小于此值 iOS 聚焦时会强制放大整个页面。
* **失败文案分流**：连不上时按「地址是否为回环」和「是否移动端」给出不同提示。手机 + 局域网地址的组合直接输出上面五条排查清单，而不是笼统地说「服务未启动」——后者在手机上是最具误导性的结论。

## 九、离线音频包（不依赖网络的兜底）

### 为什么需要

上一章那五条排查，前提是「电脑上的服务确实可达」。但局域网代理在真实网络里过于脆弱：

* Windows 防火墙拦截 `8788`（最常见，且首次弹窗常被误点「取消」）
* 路由器开启 AP 隔离 / 访客网络
* 公司与校园网禁止设备互访
* 手机走蜂窝数据而非 WiFi

任何一条成立，手机上就彻底没有声音。而手机通常也没有英语语音包——Android WebView 不实现 Web Speech API，浏览器也常常缺英语包。结果就是「点了发音一点反应都没有」。

所以给最高频的词做一份**预生成音频**直接打进安装包：播放本地文件，不发起任何网络请求，不受上述任何因素影响。

### 覆盖范围与体积取舍

| 方案 | 词数 | 体积 | 取舍 |
| --- | --- | --- | --- |
| 96kbps 全量 | 1456 | 约 30 MB | APK 过大，不可接受 |
| 48kbps 全量 | 1456 | 约 15 MB | 音质明显变差，等于退回「能出声就够」 |
| **96kbps L1+L2** | **616** | **11.7 MB** | **当前采用** |

只取 L1（331 词）与 L2（285 词）——这两级是学习优先级最高的部分，恰好也是用户最常点发音的部分。L3/L4 与全部例句、长句仍走代理服务。

### 关键设计：离线包不参与 mode 决策

发音的降级链是逐级的：离线包 → 本机语音 → 代理 → 云端 → 引导。

但离线包**不能**进入 `resolveMode()`。最初实现时让它在全部分支前 `return 'pack'`，结果测试立刻挂掉 6 项：未收录的句子与例句被一并带偏，反而丢掉了代理这条唯一能读整句的路。

正确的做法是把取用点放在 `speak()` 开头，按词精确匹配：

```
speak(text)
  ├─ packHas(text)?  → speakPack() 直接播本地 mp3
  │                   （失败则继续，不 return）
  └─ resolveMode() → 本机 / 代理 / 云端 / 引导
```

`packHas()` 查询统一小写并去首尾空格，因此大小写与多余空格不影响命中。包内词查不到时返回 `null`，自然落回原降级链，不会有任何行为分叉。

### 其他配套改动

* **`diagnose()`** 在代理、本机语音、云端都不通时，把 `env` 标为 `pack` 而非 `no-en-voice`——后者会让用户误以为自己必须去装语音包，而实际上收录的词本来就能读。
* **总览页提示条** 在有离线包时不再显示「目前无法发音」。此时高频词是能读的，继续告警属于虚假提示，比不提示更糟。
* **`build-apk.sh`** 增加离线包清单校验，漏同步即终止构建。音频放在 `assets/audio/` 下虽已被通配覆盖，但少一次校验就可能在某次同步遗漏后悄悄产出「必须联网才能发音」的包。

### 重新生成音频

```bash
node tools/pregen-audio.js            # 只补缺失的（默认，支持断点续跑）
node tools/pregen-audio.js --force    # 全部重生成
node tools/pregen-audio.js --limit 50 # 只生成 50 个，调试用
```

文件名用 `sha1(voice + '|' + text)` 的前 12 位，不用词本身——词里含撇号（`don't`）和连字符（`well-known`）时，在 URL 转义与文件系统上都会出问题。中途中断时已生成的文件会被并入清单，重跑即可续上。

上游限流较严，脚本沿用了代理服务那套指数退避（800/1600/3200ms + 抖动 + 丢弃失效连接），否则 600 词连续请求必然出现 `ECONNRESET`。

### 验证方式

测试 `7d` 章节的第 6 条是这套方案的核心验收标准：**把代理地址指向 9 端口（discard，必然连不通）**，模拟「手机连不上电脑上服务」，此时包内词仍必须真实播放完成（`onstart` 与 `onend` 都要触发）。这条断言保证离线包是真正独立的路径，而不是「代理还在时恰好能用」。
